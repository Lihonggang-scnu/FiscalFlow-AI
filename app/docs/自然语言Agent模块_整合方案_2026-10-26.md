# 自然语言 Agent 模块整合方案

日期：2026-10-26。状态：离线框架已实现，实时模型调用待预算执行；财税服务、任务管理和业务数据保持兼容。

## 1. 本次讨论的结论

下一项完整交付对象建议为：**自然语言财税办理模块**。它把已有财税服务和任务管理连接到 DeepSeek-V4.1-Flash-1017，让用户用正常表达完成查询、补充用途/备注、任务接续、更正、取消和删除。

采用现有 Python 环境、create_agent / LangGraph、SQLite 检查点和现有业务模块。长期偏好管理和本机可信规则维护作为独立模块接入；Agent 只读规则，不开放规则写入口。

## 2. 已核验的接入事项

现有环境：`E:\AI-Chem\ChemIntent\.venv-cpython\Scripts\python.exe`。

### 模型消息字段

当前 langchain-openai 1.7.0 的 ChatOpenAI 转换不能保留 DeepSeek 原始 reasoning_content 字段。Luna 使用合成消息完成了离线往返检查。官方协议要求开启 thinking 且携带工具时，在后续请求中传回相应字段。

因此本方案默认显式关闭 thinking。若用户选择开启，消息字段适配将作为模型模块的一部分一起交付。

模型配置为 DeepSeek-V4.1-Flash-1017，API 名称 `deepseek-flash`。密钥从现有外部位置读取，服务范围内直连。

### SQLite 连接

真实 ToolNode 离线运行表明，同步工具在线程池中执行。主线程建立的默认 SQLite 连接不能直接交给它使用。

业务工具使用数据库路径，在执行工具的线程内创建、使用并关闭 TaxDatabase；同一次业务操作中的服务和任务管理共用该次连接。业务写入按顺序处理，继续使用现有事务和幂等机制。

框架检查点的连接由其专用适配器管理，不与业务连接混用。详细离线观察见 `research/agent_integration_compatibility_20261026.json`。

## 3. 企业与用户范围

用户身份由程序固定。业务工具允许提供企业参数，未提供时使用当前办理企业；每次仍由现有权限服务检查目标企业。

另提供 switch_company，专门改变当前办理企业，并与界面选择器使用同一个状态。

| 用户表达 | 行为 |
|---|---|
| 当前甲企业，“查一下乙企业 9 月金额” | 临时查乙企业，当前办理企业仍为甲 |
| “切到乙企业，继续乙企业的任务” | 检查权限，切换当前企业，加载乙企业任务 |
| “把乙企业 F004 用途填为会议资料” | 处理明确指出的乙企业对象；不隐式切换当前企业 |
| “继续剩下的票” | 使用当前办理企业的任务；范围仍不明确时追问 |
| U002 请求乙企业数据 | 返回无权限，不查询或返回金额 |

所有工具结果显示企业标识，引用对象同时包含企业和发票号。切换企业后，不把另一个企业的未限定对象当成当前默认对象。

同一轮发生企业切换后，后续默认企业操作必须使用更新后的状态。实现时处理好框架一次返回多个工具调用的情况，不能只假定执行顺序会自动更新每个调用看到的状态。

## 4. 每次模型调用的上下文

按当前需要组织：固定办理说明、程序绑定的用户与权限、当前办理企业、当前相关任务、近期明确对象、必要规则和近期对话。

近期对象主要记录企业、发票号和对应来源，帮助理解“刚才那张”。金额、用途、备注与保存版本取自可信的当前业务查询。旧对话用于理解指代，当前业务结果用于办理。

有明确企业或发票引用时使用它；没有时再使用当前办理范围。出现多个符合对象时列出候选并追问。

企业切换、任务更正、保存结果和规则变化应在下一次模型调用前反映到上下文。不会机械加载全部历史，也不采用统一的七天遗忘期限。框架消息裁剪保持工具调用和对应结果的关联完整。

示例：F002 补用途后已退出 all_missing 待办，用户说“刚才那张再加备注”，仍应通过近期引用找到 F002，并查询它的当前备注。任务待办不承担全部对话引用功能。

## 5. 保存工具与任务的关系

对模型提供统一的发票字段修改工具，程序调用现有 update_invoice。它可以处理任务中的待办，也可以更正已经补好的发票。

保存和回查成功后，刷新该用户、该企业相关的进行中任务。这样，已从待办移除的 F002 仍能补备注或更正用途，不受任务目标清单的限制。

程序从实际查询结果取得 revision，并与本次修改内容一起确定操作。模型填写业务目标和内容，不自行编造版本号。

用户要求“追加备注”时，结合实际当前值处理。追加还是替换无法确定时追问；已有明确要求时直接办理。

## 6. 操作编号、重复请求和冲突

### 一次操作的身份

为一次明确的保存动作建立稳定操作编号，绑定用户、企业和发票。操作编号、原始修改内容及预期版本放进可恢复的会话操作状态，复用现有 operations 表取得已提交结果。

框架 tool_call_id 可作为关联信息。其跨中断行为尚未核验，不把“新模型调用会产生相同编号”作为前提。

同一操作重放沿用原编号和原请求快照，不能重新查询 revision 后改变原请求再沿用旧编号。用户提出新的修改要求时建立新操作。

### 两种不同结果

- 找到该操作的成功记录：回复本次操作已经保存，返回原结果。
- 当前值恰好已经等于目标值：回复“当前已经是这个值，本次无需再修改”。这表示当前目标已满足，不据此声称原操作一定执行过。

当前值与原读取值不同，则向模型返回实际差异，结合用户当前要求重新处理。权限不足、对象不明和数据冲突分别反馈，不统一包装为自动重试。

## 7. 中断后如何继续

不采用“收到新消息前无条件执行完上轮所有工具”的方式。

示例：上轮准备保存 F002 时程序中断，用户重开后说“不要保存了，取消”。系统应尊重这个新要求。

恢复时区分：

1. 已提交但缺回执：从已有操作记录取回真实结果，告诉用户发生了什么；取消后续办理不撤销已保存内容。
2. 尚未执行的写入：先处理用户当前的取消、更正或继续意图，避免自动执行已经被撤回的要求。
3. 状态尚不能确定：先查询操作和发票当前状态，获得足够信息再继续。

框架消息历史也要保持完整；补齐中断工具的结果可以是“已提交”“未执行/已取消”或明确的未知结果，不等于必须重新执行业务写入。使用框架现有状态和恢复接口实现，不另建恢复框架。

## 8. 本模块的完整使用范围

- 自然语言查询发票金额、银行收入和支出，注明范围和必要依据。
- 查看单张发票的当前用途、备注及其他只读字段。
- 查询和解释当前规则。
- 缺月份、对象或修改内容时追问，并接住后续补充。
- 创建、查看、接续、更正、完成、取消和删除任务。
- 补用途、修改用途、替换或明确追加备注，实际保存后回复结果。
- 一句话包含多项明确要求时按顺序办理，分别说明结果。
- 理解明确对象和“刚才那张”等可确定引用，有歧义时追问。
- 处理只读权限、无记录、超范围、版本冲突和接口失败。
- 查看一轮实际使用的模型输入、任务、规则、工具结果和用量。

不同自然语言说法最终调用同一业务能力，不能依靠固定问答脚本实现。

## 10. 后续独立模块

### 长期偏好管理

保存用户明确提出的稳定偏好，提供查看、更正、删除和跨会话使用。删除后的偏好不从历史消息或摘要里重新当成活动偏好。它通过清楚的接口加入上下文，不与业务任务和金额混存。

### 规则维护（已完成本机可信 CLI）

用途规则采用结构化条件，例如 all、amount_gte 与对应门槛。正文、条件、企业、生效日期和版本一起维护；表达不了的规则保留可查并给出不能自动判断的结果。

启用版本的正文和条件保持稳定，变化时创建新版本；本机可信维护入口可以导入、查找、更正新版本、启用和停用。原始资料初始化不能覆盖后来维护的当前版本；停用最新版本不自动恢复旧 inactive 版本。

规则变化后 all_missing 重新核对并说明待办变化原因；无法取得规则依据时保留旧待办并返回 warning，不阻塞金额查询；selected 仍按用户明确目标办理。

### 界面与交付

Chainlit 使用现成的 Agent 和业务接口，显示当前企业、任务、办理回执和过程记录。启动说明、设计说明及比赛材料随功能整理。

## 11. 实施组织

主要新增 provider、tools、agent/context 和每轮过程查看能力，并扩展现有配置和交互入口。职责简单时合并文件，不为命名拆空层。

复用框架保存对话状态；动态组装的实际输入及办理结果由简明的本轮记录保存，支持查看。密钥和请求认证信息不进入业务记录。

继续使用现有环境，业务工具在其执行线程中打开短连接。用户身份固定、目标企业按权限校验，工具写入顺序明确。

内部编码可以分步骤，但本模块按第8节的完整使用范围交付。真实业务使用和必要检查用于发现问题、指导修正；不把仅连通模型或单个查询作为交付终点。
