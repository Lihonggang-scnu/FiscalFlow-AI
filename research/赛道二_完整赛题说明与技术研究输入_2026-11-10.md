## 4. 赛题真正要解决的问题与三个业务场景

【官方要求】在连续财税办理中，助手可能忘记前文、混用企业信息、沿用旧规则、漏掉待办，或声称保存成功而实际没有写入。Harness 是连接模型、记忆、知识和业务工具的运行程序。参赛者需要让它根据任务状态决定下一步，而不仅是完成一次问答。[S1][S1]、[材料包《参赛说明》][PACK]

| 场景 | 用户需求 | 必须完成的处理 |
|---|---|---|
| 查询资料 | 查询指定企业、月份的发票金额、银行收入和支出，以及填写要求 | 读取当前业务数据，由程序分别计算；选择适用规则；回答金额和依据 |
| 补充并保存 | 补充指定发票的用途或备注 | 明确企业、发票、要改的内容和用户权限；仅修改获准字段；保存后重新读取核对 |
| 多轮检查 | 检查哪些发票缺用途，随后分轮补充 | 保留当前企业、月份和未完成事项；接住补充、更正；保存后更新剩余清单和任务状态 |

三个场景共用同一套处理流程。可以共用一个 Agent、工具集合和持久任务状态，由当前信息决定调用顺序。**是否有独立 Planner 类、多 Agent 或任务 DAG，不是官方指定的实现条件。**有规划、执行、结果核对的真实行为才是需要呈现的能力。

只允许修改发票用途和备注。企业、编号、日期、金额、销售方、票面项目及银行记录不可修改。不执行真实记账、付款、税务申报。

## 5. 基础能力：原始条款与含义

以下六条引文来自用户已提供、并与 11 月 2 日包核对一致的《参赛说明》v1.1.0。“含义”是整理说明，不增设官方门槛。[资料包原文][PACK]

### 5.1 对话与决策

> 模型理解用户需求，根据当前信息决定查询、追问、调用工具或结束任务。不能用关键词匹配、固定场景分支或背好的回复代替模型理解。

含义：程序可以做计算、权限及规则判断，也可以为工具设置固定业务步骤；但不能用预写场景脚本替代模型理解用户问题。换一种说法、同句提出多件事、追加更正，都应围绕真实意图处理。

### 5.2 记忆管理

> 保存任务进度和用户明确提出的长期偏好，支持查看、更正和删除；新开对话后仍能合理使用，不混用不同用户、企业的记忆。初赛每个用户在每家企业最多保留一个未完成任务。

含义：聊天记录、未完成任务、用户偏好、企业上下文不应被混作一段历史文本。新会话应能接续任务，但接续不等于自动获得写入授权。只在用户明确要求长期记忆时保存长期偏好；一次性表达要求与长期偏好应区分。

“每个用户、每家企业最多一个未完成任务”是**初赛明文范围**。将其用于初赛不能直接判为不合规；商业产品或复赛需要多个期间、多个任务时，才形成进一步扩展课题。

### 5.3 知识库管理

> 支持导入、查找、更新和停用规则。回答注明规则名称和版本，资料不足时直说。管理操作可通过命令行或其他简单入口完成，不要求制作管理后台。

含义：规则更新后，适用依据和实际执行应能随之改变；仅把静态规则塞进 prompt 不足以覆盖规则管理要求。是否采用向量检索由队伍决定，规则管理后台不是硬性要求。

### 5.4 本轮模型输入与上下文

> 选择本轮需要的对话、记忆、规则和工具结果，控制输入长度，保留企业、月份和未完成事项。需要当前业务数据时重新查询。

含义：既要控制输入，又不能因截断丢掉关键事实；旧聊天中的金额、用途及规则结果不能永远充当当前数据。任务、偏好、规则和当前数据库的更新时间及用途不同，技术方案应明确各自何时读取。

### 5.5 数据操作与工具执行

> 程序负责金额计算、参数检查、权限检查和保存；按用户明确要求修改，保存后重新查询确认。失败时说明原因，不误报成功，不重复修改。

含义：模型理解修改意图，程序执行实际权限、对象、字段和金额约束。需要区分处理中、成功、失败；重复指令、故障、用户取消或改口后，不应继续执行不再有效的旧修改。具体实现方式由队伍决定。

### 5.6 运行记录

> 能查看本轮模型输入、选用的记忆与规则、工具调用及结果，说明答案和操作从哪里来。不要记录模型密钥。

含义：评委要看得到实际送给模型的内容、选择了哪些记忆/规则、执行了什么工具及结果。普通用户界面可以简洁，检查入口可以展开详细信息。这里要求的是实际输入与执行信息，不是编写一段虚构的“AI 思考过程”。

### 5.7 自然表达（官网单列的基础能力）

《参赛说明》原文：

> 回复应像正常业务交流：直接回答当前问题，准确说清已完成和未完成的事，少套话、少重复。只追问缺少的信息，接住用户的补充和更正，保留必要的说明与依据。

含义：自然表达是题目本身，不是界面美化之后才考虑的装饰项。判断应同时看简洁程度、事实准确、任务状态和对补充/更正的理解。表格本身不违规；无论用户问什么都输出固定长清单，才是需要改善的行为。

### 5.8 官方允许的实现规模

原始材料明确：开发语言、模型和框架不限；允许简单文本检索和本地存储；不强制网页界面、向量数据库、多 Agent 或复杂运维；初赛不要求发票图像识别，数据已整理为 Excel。官网基础范围是少量数据、一个 AI 助手、顺序操作。[S1][S1]、[资料包][PACK]

【本方研究目标】这些是允许的起点，不是我们追求的上限。我们希望基础能力完整，再做有针对性、可比较、能解释收益的机制创新。

### 7.2 R001：金额统计说明 1.0

1. 发票金额为价税合计。发票总额是所选企业、所选月份**全部**发票金额之和，是否填写用途不影响统计。
2. 银行收入、支出按方向分别求和；不能混入另一方向，也不能用收入减支出来冒充支出总额。
3. 金额单位元，保留两位小数；使用十进制金额或整数分。不要求拆税额、算税率或生成会计分录。
4. 发票月份看开票日期，银行月份看交易日期。用户未说清、前文也无明确月份时应追问，不能自动换成当前月份。
5. 发票总额与银行支出可以不同；没有逐条匹配要求，不能据差额判断错误、欠款或已经付款。
6. 查询成功但无匹配记录时返回 0.00 并说明无记录。失败、无权限与无记录是不同结果。
7. 金额和保存状态以系统当前数据为准。规则文档和 Excel 核对值只能解释和检查，不能替代实际查询。

### 7.3 R002：甲企业旧版与新版

- 旧版 1.0 曾规定金额 ≥1000.00 元必须填，低于门槛可不填；只有空格也算未填。该版本**已停用**，保留是为了检验版本管理。
- 2026 年 9 月必须使用 2.0：**每张发票必填用途，无金额门槛**；空白/空格算未填，备注不能代替用途。
- 检查当前发票并列出缺用途编号。补充时明确企业、发票、内容，检查修改权限，保存后重新读取核对。
- 企业编号和发票编号共同定位；不能改到另一企业同号发票。
- 仅查询数据或询问规则不构成修改授权。
- 回复应注明《甲企业发票用途规则》2.0 版。初赛不考历史规则恢复，不需要为了 8 月用途恢复已停用的 1.0。

### 7.4 R003：乙企业发票用途规则 1.0

- 金额 **≥1000.00 元**必须填用途；等于门槛算必填，低于门槛允许不填。
- 空白/空格为未填写，备注不能代替用途；检查使用当前金额和用途。
- 不能把甲企业“每张必填”套给乙企业，也不能把可不填的票列为不符合要求。
- 用户可以主动补充低于门槛的票，但仍需要修改权限和明确的企业、发票、内容。
- 回复注明《乙企业发票用途规则》1.0 版。

### 7.5 R004：银行资料说明 1.0

- 企业编号与流水编号共同确定记录，同号可出现在不同企业。
- 交易日期决定查询年份、月份。
- 收入、支出金额都是正数，以方向字段区分，不再人为给支出加一次负号。
- 对方名称和备注只说明流水，不能据此推断某张发票已付款；同金额、相近日期或同一交易方也不能建立官方未提供的票款关系。
- 银行资料全部只读，不能新增、删除或修改。
- 查询先核对用户权限与企业范围；汇总按 R001 分别统计。

### 7.6 对创新路线的直接约束

任何新记忆、规划或检索机制都要保持以上业务语义：不能为了“智能”自动猜用途、推断付款、扩大权限、恢复停用规则，或把历史缓存当当前数据。发现缺信息时，好的改进应减少**不必要**的追问，并把**必要**的问题问得更准确，而不是取消所有追问。

## 11. 当前项目：云端可理解的实现摘要

**核对口径：2026-11-10 只读当前代码及既有验收材料。本轮没有启动服务、重新跑业务测试或调用付费模型。下列历史测试只证明其当时记录的版本和范围。**

### 11.1 已有系统结构

项目名为 TaxAgentHarness，主要使用 Python、LangChain/LangGraph、SQLite 和 Chainlit。运行方式可概括为：

```text
网页或命令行输入 + 程序确定的用户身份/当前企业
    → Agent 理解当前请求并选择工具
    → 查询 / 读取规则 / 任务管理 / 偏好管理 / 发票保存
    → 程序负责权限、金额、规则条件、事务、版本和回查
    → 当前业务状态回到 Agent，生成业务回复
```

三个官方场景已经接入同一 Agent 的工具集合，不是三个完全独立的演示脚本。模型选择步骤；程序执行确定性约束。现有实现没有单独的确定性规划器，这一点本身不构成违反官方要求。

### 11.2 存储与上下文机制

| 对象 | 当前做法 | 仍需关注什么 |
|---|---|---|
| 当前业务数据 | 导入 Excel 后存 SQLite，保存后回读；原 Excel 保留 | 后续查询必须重读当前库 |
| 任务进度 | 按用户、企业隔离；初赛每个用户在每家企业最多保留一个未完成任务 | 自动接续主要看当前企业，其他企业待办不会集中提示 |
| 任务范围 | 支持检查全部缺项、或只跟进明确选中的票 | 需要保持选定范围，不能擅自扩张到全企业 |
| 长期偏好 | 独立存储；用户通用值和企业覆盖值；查看、更正、删除；临时要求优先 | 当前主要是表达偏好，不等于通用情节记忆或可学习的办事经验 |
| 偏好类别 | 语言、详略、结果/依据顺序、金额排列、回答格式 | 是否增加新类别需明确业务价值，不能改变权限和规则 |
| 规则 | 保留版本、企业、生效日期、状态、正文及结构化条件；CLI 管理 | 正文与执行条件的语义冲突尚缺系统化导入检查 |
| 规则执行 | 支持每张必填、金额阈值、无需填写等受控条件 | 通用复杂条件尚未完整支持 |
| 模型输入 | 每次调用前刷新当前任务、可访问企业和生效偏好；保留最近 8 轮用户对话窗口 | 不是按实际 token 预算做语义选择；没有已完成的动态长对话摘要机制 |
| 会话与操作 | 保存 Agent 会话、工具操作状态及 checkpoint | 要区分新会话恢复任务与重新执行旧写入 |
| 对话历史 | 持久保存；查看、继续、复制、展开收起 | 历史可回看不等于全部历史已供模型准确利用 |

### 11.3 保存与恢复

现有保存流程会检查企业和对象、权限、可改字段、版本；绑定操作标识，经过事务和重复操作判断；保存后回读，再刷新任务。运行中断后有恢复已提交写入回执的处理。后台工具错误会转成结构化结果供模型解释。

这些实现有实用价值，也符合题目要求。要支持创新性，仍需说明相对于常规做法在哪种故障或复杂交互下提高成功率、减少重复写入或降低成本。

### 11.4 当前值得明确的限制

1. **模型配置目前硬限 DeepSeek。**根版和三页候选版的 `provider_config` 都会拒绝非 `deepseek-flash` 的模型名；模型构造还拒绝非 `https://api.deepseek.com` 的地址。当前环境变量可换 Key，但不能仅靠换 Key 完成 Qwen 切换。这是交付适配缺口；不要求现在停止 DeepSeek 开发。
2. **初赛用途任务限定 2026-09。**这符合原始初赛范围；要处理商业多期间或复赛新数据，则需扩展。默认 C001/C002 规则和官方文件初始化路径也应与通用业务配置区分，不能误把样本编号当所有企业的固定规则。
3. **长对话仍以最近 8 轮窗口加结构化状态为主。**它能保住已进入任务/偏好的信息，但没有证明那些尚未结构化的旧承诺、待确认内容和更正链始终保留。
4. **切换企业存在人为分轮约束。**当前 prompt 和工具批次保护要求先完成切换，再继续其他操作；“切到乙企业并查九月”可能需要额外一轮。这是自然办理体验的改善点，不是官方要求用户必须分轮说。
5. **基础规则更正可用，但语义冲突和复杂规则适应能力有限。**不能把已实现的版本管理等同于任意规则理解与更新都可靠。
6. **通用聊天和企业业务扩展尚未统一。**两个入口的身份、数据库及业务上下文分别管理；把模块并列介绍时不能写成单个 Agent 已无缝办理全部业务。
7. **最终提交版本尚需统一。**旧交付记录中有 ZIP、演示及设计说明，但它们早于后来的企业扩展和三页候选；这轮未重新验收最终提交物。

## 12. 对照四个评分维度，当前差距在哪里

以下为本方评估，不是官方打分，也没有把“基本合格”当作完成目标。

| 维度 | 已有基础 | 冲高分还缺的关键内容 |
|---|---|---|
| 完整度 45% | 三场景共用 Agent；程序计算、权限与保存回查；任务/偏好/规则管理；界面与运行信息 | 官方模型配置适配和最终版本验收；变化、故障、复杂表述中的稳定性；提交物对应同一可运行版本 |
| 契合度 20% | 已区分模型决策与程序执行，业务规则理解较完整 | 减少人为额外分轮、无关解释；用连续任务呈现模型如何依据反馈调整；企业扩展应围绕赛道核心讲清价值 |
| 完善空间 10% | 工具和服务有模块边界；企业扩展有可用实现 | 多入口整合、可配置的期间与规则、长上下文策略，以及清楚且可验证的迭代路径 |

**是否把基础当特色：确实需要纠正宣传和目标的重心。**跨会话任务、偏好 CRUD、规则版本、权限、回查、日志这些已经是题目基础。此前企业方案已写明规则/权限/恢复不单独包装成创新，这个判断应保留。问题在于：现有交付证据主要证明功能能运行，尚缺足够材料支撑新标准下占 25% 的创新价值。

C1 可以作为特色候选，但“自由文本提取成字段”本身也是常见能力。更有说服力的贡献应是它对歧义、跨票指代、更正、多轮补充、复杂任务接续等难点的处理机制及效果。C2 当前只是计划，不能用规划代替已实现成果。

## 13. 面向高分的验收目标（我方建议，非官方另加门槛）

### 13.1 必须稳住的业务结果

- 原始样本的六组企业/月度统计符合第 6 节；当前数据变更后，重复提问反映新值。
- 两个用户的权限、企业边界、同号发票定位正确；未授权写入为零。
- 所有确认写入均回查一致；只改允许字段；重复请求不造成重复修改；失败不报成功。
- 9 月缺项与规则版本正确；空白、空格、仅有备注、999.99/1000.00/1000.01 边界都处理正确。
- 新会话恢复任务/偏好；更正、删除后旧值不再支配后续结果；恢复任务不自动执行用户未授权的修改。
- 规则可导入/查找/更新/停用，模型引用名称版本；缺依据时说明不足。
- 能查看实际模型输入、采用的状态及工具结果；用户回复自然、直接，不反复追问已知信息。
- 最终程序使用官方指定配置运行同样的业务链路，并完成可重现的启动和材料核对。

“数据错、越权、状态错、保存误报”等应单列，不能被总体通过率平均掉。这是我们的质量目标，不是官方公布的分项扣分公式。

### 13.2 用进阶实验支撑特色

| 实验主题 | 要回答的问题 | 建议观察项 |
|---|---|---|
| 超过最近 8 轮的信息保持 | 更早承诺、待确认项及其更正是否仍正确可用？ | 任务完成率、关键事实遗漏、错误恢复旧值、输入 token |
| 记忆更新与企业切换 | 偏好撤销、月份更正、临时跨企业查询后，状态是否正确？ | 跨企业串用、过期记忆使用、额外追问次数 |
| 规则变化与外部数据变化 | 旧推理是否被适当地更新，影响哪些未完成事项？ | 规则选用准确性、任务清单正确性、重做量 |
| 写入回执丢失、重启、超时 | 能否查清实际提交结果后继续？ | 重复写入、误报、恢复成功率与时间 |
| C1 复杂口语回复 | 一句话涉及多票、否定、更正、部分补充时能否准确拆解？ | 每票字段正确率、歧义识别、人工确认/返工次数 |
| 自然交互 | 能否以更少无效往返完成同一任务？ | 必要/不必要追问、任务完成时间、回复事实与状态准确性 |

对比方案可包括当前“最近 8 轮 + 结构化状态”、常规全历史输入、简单检索式记忆，再与候选新机制比较。保持业务工具、任务集和模型条件可比；说明不同模型分别测试了什么。需要重试、一致率和长对话实验时，要在有限预算内挑能区分方案的用例，不用大量低价值重复请求替代分析。

实验应保留未用于调参的任务，覆盖新表述、跨轮更正和组合条件；扩展测试可增加企业、编号、期间、规则及异常数据，用独立程序或人工标注给出预期结果。官方原始样本用于基础核对，新增数据用于判断泛化和产品能力，分别报告。扩展实验不改变初赛原有的 9 月用途检查范围，也不能把官方未提供的票款关系添加成事实。

官方没有指定“至少多少轮、多少企业、多少测试用例或多少通过率”。上表是我们设计实验的方向，具体数量与预算应在选定路线后确定。

## 14. 交给云端助手的技术研究任务

以下为用户目标：**不满足于基础功能齐全；希望从近期顶会、顶刊及高质量最新研究中找出适合本题的机制，例如 Agentic Memory，形成真正有针对性的强项。日常开发继续用 DeepSeek V4.1 Flash，交付前再用 Qwen3.8-Max 测试。**

### 14.1 候选问题，应围绕业务难点研究

1. **主动管理的长期记忆。**如何决定保留什么、何时更新/合并/遗忘、如何处理更正和冲突，既保住未完成事项，又避免过期记忆干扰？与现有偏好表和任务表如何分工？
2. **任务反馈驱动的规划调整。**如何根据工具结果、用户改口、规则变化及中断状态更新计划，而不是固定往下执行？是否能减少重复查询或不必要追问？
3. **有限输入下的上下文选择。**如何选取本轮真正需要的对话事实、任务状态和规则，使长对话仍准确，并用费用/延迟数据说明取舍？
4. **规则变化影响下的任务接续。**能否把变化对当前目标和待办的影响表达清楚，并调整后续行动？现有版本管理与可选 C2 之间有什么实质增量？
5. **面向会计办理的交互决策。**对多张票、跨轮指代、部分回答和歧义，应先处理哪些已确定事项、合并询问哪些真正缺失的信息？如何衡量沟通成本下降？

这些是研究问题，不是已选架构。可以提出更好的方向，但必须解释它解决第 4—8 节的哪个难点。

### 14.2 对技术调研输出的要求

- 提出 2—3 条有实质差异的路线，每条引用相关原始论文/正式项目；给出名称、作者、年份、会议/期刊或预印本身份、原文链接。
- 核实论文实际状态；仅有预印本时明确标识，不能冒称已被顶会接收。优先近期工作，同时保留必要的经典基线。
- 解释机制与本题的关系：记忆的数据单位、写入/检索/更新条件、如何接任务状态、怎样使模型据反馈调整行动。
- 说明与常规工具 Agent、固定窗口、普通 RAG/检索式记忆相比，新增了什么，并给出区分效果的实验。RAG 可作为工具或对照；仅组合一个常规检索流水线不满足用户希望形成强项的目标。换成“Agentic Memory”名称也不能自动证明更好。
- 明确复用现有模块、需要新增的最小完整模块、输入输出、存储与运行路径；一个模块可以小，但要完成其完整使用周期。
- 给出失败方式、适用范围和必要的对比/消融。比较正确率、错误类别、无效追问、耗时、token 与单位完成成本，不只看回答流畅度。
- 分开给出：比赛必须修复项、最有希望支撑创新分的机制、面向企业产品的额外能力。不要把生产平台建设全部塞进初赛。
- 尊重预算：先用现有 DeepSeek 开发和验证候选，再在交付前用 Qwen 检查关键迁移；不要把大规模 Qwen 调用或训练新模型作为默认前置条件。
- 推荐路线时给出选择理由、实施次序与验收标准，不虚拟官方得分，不承诺“用了某论文就拿满分”。
