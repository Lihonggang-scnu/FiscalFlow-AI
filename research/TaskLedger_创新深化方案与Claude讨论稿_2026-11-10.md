## 2. 项目与比赛背景

### 2.1 官方目标

作品要用一套 Agent 运行流程处理三个连续场景：

| 场景 | 需要做什么 |
|---|---|
| 查询资料 | 查询指定企业、月份的发票总额、银行收入和银行支出，解释适用填写要求 |
| 补充并保存 | 根据用户要求补充发票用途或备注，检查对象和权限，实际保存并回查 |
| 多轮检查 | 检查缺用途发票，在连续对话、新会话和用户更正之后接着办理，更新未完成事项 |

模型承担需求理解、追问、选择工具和反馈调整；程序承担金额计算、权限、字段限制和业务保存。官方基础能力还包括任务与长期偏好管理、规则导入/查找/更新/停用、上下文长度控制、查看实际模型输入与执行记录、自然准确的业务表达。

官网四项进阶方向为：长对话摘要；记忆/规则/企业/数据变化后仍能正确处理；工具超时或重启后的任务恢复；不同记忆、检索和输入策略对正确率、耗时、费用的对比。

### 2.2 评分与模型策略

11 月 6 日最新统一评分：作品完整度 45%、问题理解与方案契合度 20%、后续完善空间 10%、创新性 25%。基础功能完成后，需要有针对性的机制和实际收益来支撑创新性。[官方公告](https://www.saikr.com/c/nd/50274)

官方初赛跑测模型为 **Qwen3.8-Max**。我们的预算有限，用户已确定：**日常开发与实验使用 DeepSeek V4.1 Flash，交付前再使用 Qwen3.8-Max 测试。**官方模型名称已明确，具体 API 标识、地址和评审环境仍待主办方配置说明；适配设计采用可配置模型信息即可。

作品提交截止日期为 2026-11-13。最终材料包括代码、依赖及启动说明、设计说明、关键运行记录和不超过 5 分钟的演示。当前这轮任务是完善技术路线，暂不执行新的付费实验。

### 2.3 会影响技术设计的业务约束

- 只能修改发票的用途和备注。金额、日期、销售方、票面项目及银行记录不允许修改。
- 用途必须来自用户提供的实际业务信息，不能依据销售方或票面项目自行猜测。
- 发票和银行记录没有逐条对应关系，不能推断付款或欠款。
- 用户身份由程序确定。U001 可查看并修改甲、乙两家企业；U002 只能查看甲企业，不能修改，也不能访问乙企业。
- 初赛用途检查限定 2026 年 9 月；8 月用于金额查询。每个用户在每家企业最多一个未完成任务。这两条属于初赛范围。
- 甲企业 C001 的 9 月用途规则为 R002 2.0：每张必填；旧版 1.0 已停用。
- 乙企业 C002 的规则为 R003 1.0：金额 ≥1000.00 元必填，低于门槛可不填；空格算未填，备注不能代替用途。
- 查询需要当前数据时重新读取；新会话恢复任务不意味着自动取得写入授权。
- 长期偏好只有用户明确要求长期保存时才持久化；支持查看、更正和删除。企业偏好可覆盖通用偏好，本轮临时要求优先。

## 3. 我们已经具备的基础

项目名 TaxAgentHarness，主要使用 Python、LangChain/LangGraph、SQLite 和 Chainlit。

```text
聊天/CLI + 当前用户身份
    → 同一个 Agent 理解需求、选择工具
    → 查询 / 规则 / 任务 / 偏好 / 保存工具
    → 确定性业务服务与 SQLite
    → 工具结果和当前状态返回模型
    → 业务回复与界面更新
```

目前可以复用的能力：

| 已有模块 | 能力 | 新方案可以怎样接入 |
|---|---|---|
| AgentRuntime | 模型工具循环、会话、checkpoint、停止与错误反馈 | 在模型调用前编译上下文，在工具返回后更新计划与记忆 |
| 业务服务 | 整数分金额计算、权限与可改字段检查、事务、保存回查 | 继续作为业务数据与操作结果来源 |

| 偏好管理 | 通用/企业范围、查看、更正、删除、新会话生效 | 增加更正历史及与当前表达策略的联系 |
| 规则管理 | 文档版本、生效日期、状态、结构化条件、CLI 维护 | 产生规则变化事件，支持影响计算 |
| 操作记录 | 操作标识、重复操作处理、保存回执和恢复 | 继续处理实际写入与中断恢复 |

| 企业 C1 | 经办人自由回复拆成逐票草稿；会计确认、复核、关闭与导出 | 接入跨轮草稿、问询规划和任务记忆 |

当前模型输入主要采用最近 8 轮用户对话，加每次读取的任务、可访问企业和有效偏好。任务和偏好已有结构化存储，但更早的未决问题、未进入任务表的承诺、跨轮草稿及更正关系还没有统一处理机制。

其他与新方案有关的现状：

- provider 目前锁定 DeepSeek 模型名和地址，需要改成可配置切换。

- 通用聊天与企业工作台的身份、数据库和业务上下文尚未打通。
- 企业 C1 的单次提取范围最多 20 张票。
- C2“规则变化影响预览”尚待实现。

新设计优先接在上述能力上；不需要因为引用新论文而更换整套框架或数据库。

## 4. 原 TaskLedger 方案的核心思路

原方案选择三条路线中的状态账本路线为主干：

| 路线 | 关键内容 | 与当前深化方向的关系 |
|---|---|---|
| 状态账本 | 双时态条目、上下文编译、依赖失效 | 用于连续办理的核心状态 |
| 经验手册 | 从成功和失败中提炼策略，离线改进后使用 | 用于改善如何办理与如何询问 |
| 语义记忆 | 内容抽取、关联、检索 | 可作为查找候选记忆的方法和实验对照 |

其六个主要部件如下。

### 4.1 带时间、范围和关系的任务账本

账本记录目标、待办、未决问题、用户决定、草稿、更正和派生结论。每条记录知道属于哪个用户、企业和任务，来自哪轮对话，何时有效，以及依赖什么。

例如“甲企业只跟进 F003、F009”不再只是聊天中的一句话，它会成为当前任务范围；“F009 的用途还没问清”成为未决事项；后来改为 F006 时，旧目标与相关草稿按关系更新。

### 4.2 上下文编译器

模型每轮需要的信息由任务状态组织：当前目标、企业月份、待办、相关规则、有效偏好、当前工具结果、必要原话。不同内容有不同优先级与输入预算，需要时再回看旧话语。

### 4.3 依赖失效与重规划

规则、数据或用户要求改变时，先找出受影响的结论和行动，再重新计算或调整后续步骤。C2 可以在此基础上展示规则变化会增加或减少哪些待办。

### 4.4 写入与恢复

沿用业务保存、回查和操作回执。出现超时、崩溃或回执丢失时，先弄清上次实际执行情况，再决定继续哪一步。

### 4.5 结果卡与自然表达

用结构化业务结果组织回复：完成了什么、哪些还没完成、依据是什么、下一步真正需要什么。用户看到自然语言，界面也能据同一结果更新。

### 4.6 可以改进的经验手册

从实际办理中提炼策略，比如怎样处理多票回复、怎样接住更正、什么时候合并追问。手册改善交互和行动选择，业务金额、权限和规则仍由原有业务模块处理。

**值得延续的设计深度：每个想法都进一步说明“解决哪个痛点、如何运行、保存什么、接在哪里、怎样比较效果”。**后文按这个深度继续展开。

## 5. 从 Duang777 项目中吸收什么

这里关注能推动本项目的设计思想与实现方法。

### 5.1 Helios：把自然语言目标变成可执行计划

Helios 的编译器结合当前工具能力生成流程草案，校验结果会反馈给草案生成器；运行时按依赖和条件推进步骤，前一步的结果进入后续变量。[编译器](https://github.com/Duang777/helios/blob/a5ed6abf664e92d68c6b4965ca40b8e9ab359403/backend/internal/compile/compiler.go#L86)、[执行引擎](https://github.com/Duang777/helios/blob/a5ed6abf664e92d68c6b4965ca40b8e9ab359403/backend/internal/runtime/engine.go#L183)

对我们的启发：用户的一句话可以形成一份带前置条件的办理计划。需要补充的信息、可立即执行的步骤、完成条件都成为可操作对象。用户更正时，模型修改计划中的相关部分。

不必移植它的 Go 后端。我们可以在现有 Python 工具循环中加入计划对象和计划更新工具。

### 5.2 Dharness：让“没有进展”参与下一步决策

Dharness 在发现重复循环或连续停滞时，把情况反馈给模型并促使其重新规划；完成检查的反馈同样会进入下一轮。[重复与停滞处理](https://github.com/Duang777/Dharness/blob/da5697ab49bc13ce745c52c8246db34b8e91b56b/src/evidence_harness/run_loop.py#L762)、[完成反馈](https://github.com/Duang777/Dharness/blob/da5697ab49bc13ce745c52c8246db34b8e91b56b/src/evidence_harness/run_loop.py#L813)

对我们的启发：同一张票反复查询、同一个问题反复追问、同一种失败不断重试，都应改变 Agent 的办理方法。它可以补取缺失信息、刷新对象、修正理解、改走另一个可用工具，或只询问确实需要用户解决的问题。

这一机制应该帮助 Agent 脱离停滞，而不是再加一层会把它卡住的固定流程。

### 5.3 DeepResearch-X：记忆选择是可替换的策略

其 MemoryService 将记忆获取、排序、预算内选取、写入与存储后端分开。代码中有置信度、近期程度、冲突与衰减因素，并提供记忆方案的比较脚本。[记忆服务](https://github.com/Duang777/deepresearch-x/blob/main/deepresearch_x/memory/service.py)、[比较入口](https://github.com/Duang777/deepresearch-x/blob/main/scripts/compare_benchmark.py)

对我们的启发：把“怎样挑本轮记忆”做成可实验的策略。财税场景应加入当前步骤、未决信息、用户更正和依赖关系，而不仅按时间或语义相近程度选择。

### 5.4 ForgePilot：把上下文整理接入每次模型调用

ForgePilot 有调用前的上下文编排器，可按阈值触发整理，并生成包含目标、已完成、待办、决定等字段的摘要。[上下文编排](https://github.com/Duang777/forgepilot-agent/blob/main/forgepilot_sdk/utils/context_orchestrator.py)、[整理实现](https://github.com/Duang777/forgepilot-agent/blob/main/forgepilot_sdk/utils/compact.py)

对我们的启发：上下文策略应直接接在 Agent 的调用路径上，并能随模型配置变化；把既有近期窗口发展为“任务状态＋相关记忆＋按需原话”的组合。

### 5.5 Soular：让 AI 理解结果成为产品体验

Soular 将观点分析转成可以探索的立场光谱与地图，用户可以阅读、比较、筛选和定位自己。其语义分析结构包含立场轴、回答位置、相关程度及观点类型。[项目设计](https://github.com/Duang777/soular)、[光谱分析代码](https://github.com/Duang777/soular/blob/main/server/src/core/question-spectrum.ts)

对我们的启发：把任务、票据、疑问、更正和进度的关系呈现为可操作的任务地图。用户通过界面看懂 Agent 正在办理什么，也能直接修改目标、回答待问问题、继续某张票。

我们想借鉴的是“核心能力直接变成交互体验”的方法。适合会计的形式可以是紧凑时间线、分组待办和关系展开，不必照搬星云外观。

## 6. 深化后的总体主线

建议围绕以下闭环组织方案：

**任务记忆 → 感知变化 → 调整计划 → 选择必要信息 → 推进办理 → 积累处理经验。**

```text
用户消息 / 数据变化 / 规则变化 / 工具反馈
                    ↓
          更新任务理解与记忆条目
                    ↓
       找出受影响的结论、草稿和步骤
                    ↓
        模型更新办理计划、决定下一步
                    ↓
     编译所需上下文 → 查询 / 询问 / 保存
                    ↓
        更新实际进度与面向用户的结果
                    ↓
          办理经历进入策略改进过程
```

创新重点可以落在三个相互支撑的问题上：

1. **变化之后，哪些事情必须重新想，哪些成果可以继续利用？**
2. **完成当前目标，下一步最值得取得的信息是什么？**
3. **经过多次办理，系统怎样学会更有效的处理方法？**

下面的设计均为待共同确定的候选机制；Claude 可以加强、合并或提出替代路线。

## 7. 候选机制 A：任务记忆网络

### 7.1 记住能继续办事的对象

建议包含以下条目，而不是让所有信息都挤进一个摘要字段：

| 条目 | 示例 | 在办理中起什么作用 |
|---|---|---|
| 目标 | 完成甲企业本期指定两张票的用途补充 | 判断当前工作是否推进和完成 |
| 范围 | 甲企业、2026-09、F003/F009 | 确定工具操作与待办边界 |
| 用户决定 | F009 暂缓，等经办人回复 | 避免每轮重复催问 |
| 待问信息 | F009 的实际业务目的 | 进入问询规划 |
| 草稿 | F006 用途拟填“研发团队项目管理服务” | 跨轮继续、更正或保存 |
| 条件承诺 | 明天收到说明后，再处理剩余票据 | 恢复时知道下一步及其条件 |
| 派生结论 | 当前缺用途的是 F002/F005/F006 | 依赖当前规则和数据，可重新计算 |
| 更正 | 将此前的 F009 更正为 F006 | 更新相关草稿、范围与行动 |

条目之间可以使用少量有含义的关系：`depends_on`、`supersedes`、`answers`、`blocks`、`belongs_to`。语义检索可以找出候选关联，模型结合当前任务决定关系，程序落实到具体对象。

### 7.2 数据形态草案

```text
MemoryItem
  item_id
  user_id, company_scope
  conversation_id
  task_id / enterprise_work_item_id（有对应业务任务时关联）
  kind
  object_refs：企业、期间、票据、规则等引用
  payload：用户意图、问题、草稿或结论说明
  status：active / resolved / superseded / stale / cancelled
  source_turn_id
  valid_from, valid_to
  recorded_from, recorded_to
  superseded_by

MemoryRelation
  from_item, relation_type, to_item_or_dependency
```

并非每次资料查询都需要建立一个正式未完成任务。会话中的待确认事项可以先归属于会话，形成业务任务时再关联；原来的 TaskManager 继续管理官方任务进度。

### 7.3 两种时间分别有什么用

- **业务有效时间**：某项规则、用户安排或事实适用于哪个时间段。
- **系统获知时间**：系统什么时候收到它，什么时候收到后续更正。

例如用户今天补充“上周提供的用途说明有误”，系统既要使用更正后的内容继续办理，也要理解此前对话为何采用旧信息。可以用版本记录或状态变化事件实现，重点是表达清楚这两个时间维度。

金额、当前已保存用途等业务数据仍从业务库读取。账本可以保留查询引用、数据版本和派生结论；用户拟保存的用途作为草稿保存，与当前已写入值区分。

### 7.4 与现有表的关系

TaskManager 负责正式任务状态，偏好管理负责长期偏好，规则模块负责适用业务规则。账本补充跨轮理解所需的决定、疑问、草稿和依赖，并组织这些对象之间的关系。

云端需要帮助决定：哪些状态直接引用现有表，哪些条目需要新表，怎样避免同一项待办在两个地方各自变化。可以用现有业务服务的事件更新账本投影，让已有服务继续承担业务状态写入。

## 8. 候选机制 B：变化驱动的计划更新

### 8.1 从“重新想一遍”变成“处理受影响的部分”

当用户、规则或数据发生变化时，沿依赖关系找到受影响的结论与步骤，再把影响说明交给模型。模型据此给出计划增量：保留什么、取消什么、需要重查什么、接下来做什么。

```text
PlanStep
  step_id
  goal_ref
  action：query / inspect_rule / ask / save / wait / finish
  inputs
  dependencies
  completion_condition
  status

PlanDelta
  preserve_steps
  revise_steps
  cancel_steps
  add_steps
  next_action
```

简单问题可以只形成一个行动。复杂任务再展开为依赖计划，不要求每条消息都生成一张大图。

### 8.2 不同变化影响不同内容

| 变化 | 典型影响 | 应保留的内容 |
|---|---|---|
| 用户更正发票编号 | 旧对象的未执行草稿、相关追问和目标引用需要调整 | 与更正无关的票据进度 |
| 规则门槛改变 | 缺项判断、待办集合和办理优先级可能变化 | 用户提供的真实业务说明 |
| 另一位会计补了用途 | 原先“仍缺用途”的判断需要重核 | 当前用户的办理目标和偏好 |
| 用户说某张票先等一等 | 后续行动变为等待，暂不重复询问 | 该票已有的草稿和待确认信息 |
| 偏好改为简短回答 | 回复组织变化 | 业务数据和已经完成的操作 |
| 临时查询别的企业 | 查询使用目标企业的数据与规则 | 原办理企业的未完成任务 |

身份始终由程序绑定。需要跨企业查询时，模型提出目标企业，业务服务按当前用户权限解析和执行；这与把身份交给模型决定是不同的事情。

### 8.3 接入 C2：规则变化影响预览

对于旧规则与候选新规则，在相同业务数据上分别计算：

- 新增需要补用途的票据；
- 不再必填的票据；
- 已有用途、无需补充的票据；
- 受影响的未完成任务和后续步骤。

例如，在扩展实验中将乙企业门槛从 1000 元改为 500 元：原始样本中 F001（600 元）和 F004（999.99 元）会新增为缺用途，F009（486.75 元）仍可不填；F008 虽为 600 元但用途已填，不进入新增待办。这个例子能同时展示规则理解、影响计算和计划更新。

预览与规则正式生效采用不同动作。规则生效后，Agent 更新相关未完成任务；已结束工作如何复查，可由企业流程确定。

### 8.4 把停滞转成重规划机会

可以向 Agent 提供几种简单的进展信号：

- 新获得了什么信息；
- 哪个缺项已解决；
- 哪个草稿已保存；
- 哪个问题仍未得到回答；
- 相同操作是否一直返回相同错误。

当连续操作没有新增信息时，提示模型重新解释障碍，并选择不同的行动。重点观察它是否会从“再试一次”转向有效补查、更新计划或准确询问。

这是一个可实验的行动策略，不必先建设通用调度平台。

## 9. 候选机制 C：主动问询规划

这是在 TaskLedger 原方案上值得重点深化的方向：**让下一句问题成为任务规划的一部分。**

### 9.1 系统在选择什么

每轮先识别：

1. 哪些事项信息已经足够，可以办理？
2. 哪些事项真正缺少信息？
3. 哪些缺项可以由同一个问题一起解决？
4. 哪些需要的是工具查询，哪些必须由用户提供？
5. 哪些事项用户已明确暂缓，现在应等待？

这样，“继续问什么”就与剩余工作直接连接起来。

### 9.2 问题候选的数据结构

```json
{
  "question_id": "q-12",
  "targets": ["draft-2", "draft-5"],
  "missing_slots": ["actual_business_purpose"],
  "known_facts": ["用户已说明两张票属于同一项目"],
  "expected_progress": ["确定两张票各自的用途内容"],
  "user_effort": "一次简短说明",
  "text": "这两张票在该项目里分别用于什么？"
}
```

可以先尝试定性的选择原则，也可以实验一个简单效用函数：

```text
问题价值 = 预计推进的待办 × 当前重要程度
          + 预计减少的歧义
          - 用户回答负担
          - 已知信息的重复询问
```

这只是候选决策方法，权重由实际任务筛选。候选问题中的内容必须围绕用户真正缺失的信息，不诱导用户接受系统猜出的用途。

### 9.3 合并与分开询问都应可选择

多张票属于同一个活动时，可能适合一次询问；每张票对应不同经办人时，可能适合分别处理。目标是更少的有效沟通往返，不机械限定每轮一定问一个问题，也不要求每轮都追问。

用户已经明确要求保存、对象和内容都清楚时，直接走现有保存流程。用户只要求展示草稿时，保留草稿；用户说“等我问一下”时，记录等待决定。

### 9.4 这个方向为何可能形成强项

很多记忆方案主要改善“能否找回信息”。这里进一步研究：找回信息之后，能否利用它减少不必要的询问、合并办理、让用户更快完成任务。

可比较完成同一批票据的用户补充轮数、重复回答次数、人工输入量、返工次数和实际完成时间。

## 10. 候选机制 D：面向当前步骤的上下文编译

### 10.1 选择逻辑

上下文围绕“当前目标和下一步行动”组织：

| 内容 | 选择方式 |
|---|---|
| 身份、目标企业、期间、当前目标 | 每轮明确提供 |
| 当前行动依赖的记忆 | 按计划依赖选择，并带必要前置条目 |
| 未决事项、等待决定与用户更正 | 优先保留会影响后续动作的内容 |
| 适用规则 | 按企业、日期、状态选择当前版本 |
| 当前工具结果 | 选与本次请求直接相关的结果 |
| 近期原话 | 保留对指代、补充和表达有帮助的轮次 |
| 更早原话 | 需要核对更正、指代或原始要求时按引用回看 |
| 经验手册 | 选与当前办理情形相关的少量策略 |

### 10.2 多层表示

当待办较多时，可以采用三层表示：

- **总览层**：目标、范围、当前进度和关键未决事项。
- **工作层**：本次正在处理的票据、相关草稿、依赖及规则。
- **回看层**：其他条目和原话，用工具按需取回。

这个结构使计划和账本可以继续增长，而模型输入围绕当前工作保持集中。

### 10.3 从失败中改进选择策略

参考 ACON 的思路，寻找“完整上下文下可以完成、压缩后遗漏了关键条件”的成对案例，分析缺失的是哪类信息，再修改选择或摘要策略。[ACON](https://arxiv.org/abs/2510.00615)

例如多次发现“暂缓决定”被压掉导致重复询问，就提高未决决定的保留优先级；如果与当前企业无关的已完成事项长期占用输入，就降低其常驻优先级。

这能把输入预算管理发展成可持续改进的能力，而不是一次性设定固定窗口。

## 11. 候选机制 E：从办理经历中形成策略手册

参考 ACE 的增量整理和 ReasoningBank 的经验提炼，把成功与失败经历变为带适用条件的策略。[ACE](https://arxiv.org/abs/2510.04618)、[ReasoningBank](https://arxiv.org/abs/2509.25140)

### 11.1 一条策略应包含什么

```text
策略：多票部分回答的处理
触发情形：用户一次说明多张票，只解决部分用途
建议动作：保存明确获准且信息完整的部分；其余保留为待办；合并真正缺失的问题
适用条件：对象能够确定，当前用户具有对应权限
反例：用户明确要求全部先留为草稿，暂不保存
观察效果：完成轮数、反复追问次数、未完成事项遗漏情况
```

相比一条无条件的“以后都简短回答”，这种策略能帮助模型判断什么时候该怎么做。

### 11.2 两个并行的改进对象

- **行动策略**：下一步查什么、问什么、何时重规划、如何处理多票更正。
- **上下文策略**：哪些记忆经常帮助完成任务，哪些信息被遗漏后容易造成失败。

同一次失败可以产生两种不同改进：一是改变行动顺序，二是改变提供给模型的信息。实验应能区分它们的贡献。

### 11.3 一个完整的学习周期

1. 收集实际任务中的成功、失败和低效办理过程。
2. 模型提出新增、修订或合并的策略条目。
3. 在开发任务上比较策略前后的行为，保留有帮助的条目。
4. 将选定策略组合冻结，再在未参与选择的任务上运行。
5. 在结果中说明改善了哪些情形，下一轮继续从新的经历改进。

可以先完成一个完整周期，再决定是否增加自动化程度。提交时使用选定版本，业务规则、金额计算和权限仍由已有模块管理。

## 12. 候选机制 F：可操作的任务地图

### 12.1 页面直接表达办理关系

保留现有对话工作区作为主入口。旁边的任务区展示：

- 当前目标和范围；
- 哪些票已完成、正在办理、等待信息；
- 哪个问题阻塞哪些票；
- 最近一次更正改变了什么；
- Agent 下一步准备做什么。

可采用“任务列表＋变化时间线＋按需展开的关系”，让常用操作保持直接。

### 12.2 用户可以怎样介入

| 用户操作 | 对 Agent 状态的影响 |
|---|---|
| 选择一张票继续 | 将该票设为当前办理焦点，编译对应上下文 |
| 修改目标范围 | 更新目标与计划，整理受影响的草稿 |
| 回答一个待问问题 | 更新关联条目，重新选择可执行步骤 |
| 将某项暂缓 | 记录等待决定，调整下一步行动 |
| 展开一次规则变化 | 展示新增或减少的待办及相应计划变化 |
| 返回历史决定 | 查看当时内容，并提出新的更正 |

界面更新与 Agent 使用同一份任务状态。这样，用户通过聊天和通过界面进行的调整能够连贯衔接。

### 12.3 展示创新的方式

演示时可以让评委亲眼看到：一句更正使相关票据与待办发生变化，Agent 随即继续正确的下一步。重点呈现“理解与行动如何变化”，普通业务界面不需要铺满内部 ID 或技术名词。

## 13. 四个完整运行例子

以下为拟用于设计和实验的场景，均可由官方模拟数据派生。

### 场景一：长对话、临时跨企业查询、目标更正与外部更新

初始请求：“只跟进甲企业 9 月 F003、F009 的用途。”

之后穿插十几轮其他查询，包括临时查询乙企业。再收到：“之前编号说错了，改为 F003、F006。F009 先不处理。”与此同时，另一位会计已在业务库补好 F003。

期望运行：

1. 找回原目标与范围，理解此次更正针对哪项工作。
2. 更新为 F003/F006，处理 F009 尚未执行的草稿与相关追问。
3. 重新查询当前记录，确认 F003 已完成。
4. 将办理重点收敛到 F006，取得它仍缺少的实际用途。
5. 页面呈现范围调整、已完成事项和剩余事项。

期望业务回复可以是：“范围已改为 F003、F006。F003 的用途已经补齐，目前还剩 F006；它实际用于什么业务？”

比较重点：旧目标误用、重复询问、无关操作、输入长度和完成轮数。

### 场景二：规则变化自动调整待办

乙企业正在补用途。管理员通过规则入口把新门槛从 1000 元调整为 500 元，并指定相同适用期间。

期望运行：

1. 程序分别计算旧新规则下的用途要求。
2. 找到新增缺项及受影响的未完成任务。
3. 模型更新计划，保留已收集的真实用途和已完成操作。
4. 用户能看到新增的 F001/F004，知道原有待办与新增加的工作分别是什么。

比较重点：变化影响是否算对、任务是否漏项、是否重复处理未受影响的内容。

### 场景三：一段口语含多票、更正、保存和暂缓

用户说：“F002 是打印客户验收资料；F003 用于研发团队项目管理——编号说错，是 F006。F009 先等我问经办人。把前两张用途保存，F009 只加备注‘用途待核实’，不要补用途。”

期望运行：

- 将用途分别绑定到 F002 和 F006，F003 保持原样。
- 保存用户明确要求的内容并回读。
- F009 只补备注，用途继续为空，记录等待决定。
- 不在同一轮继续追问用户已经说要去核实的 F009。
- 下一次用户补充 F009 时，能接回这张票与未完成事项。

比较重点：每票字段正确率、更正理解、保存对象、用户需要重复说明的次数。

### 场景四：保存中断后接续

用途保存过程中回执丢失，用户重新打开对话说：“继续刚才的。”

期望运行：

1. 根据原操作记录查清提交情况，读取当前发票。
2. 已完成的操作继续使用原回执，不重复保存。
3. 尚未提交的内容按用户当前意图继续处理。
4. 当前值若已由其他操作改变，先弄清与用户目标的差异，再决定下一步。

回复应准确区分“上次已经保存”和“当前记录已是这个值”。结果明确后继续后续待办，避免把恢复变成重新开始整段对话。

## 14. 怎样接入现有系统

### 14.1 建议的衔接点

以下模块名用于本地实施时定位，云端助手只需依据这里的职责判断。

| 现有位置 | 拟增加的能力 |
|---|---|
| `agent.py` / 调用前上下文构造 | 编译当前目标、相关账本、计划、规则、工具结果与策略 |
| `agent_tools.py` | 记忆更新、计划更新、源话语回看、跨企业目标解析等工具 |
| TaskManager | 将任务进度及范围变化反馈给账本和计划 |
| preferences | 更正/删除后的有效偏好与相关表达策略更新 |
| rule_manager | 规则变化事件、影响预览与受影响任务重核 |
| services / 保存操作记录 | 继续处理实际写入、版本、回执与恢复，输出办理反馈 |
| enterprise C1 | 多票草稿接入同一记忆与问询逻辑 |
| Chainlit 及三个页面 | 展示任务地图、待问信息、草稿、变化和继续入口 |
| provider | 模型名称、地址、调用选项和预算配置分离 |

### 14.2 一轮处理的建议顺序

```text
收到用户消息或恢复请求
    → 读取当前身份、目标和必要业务状态
    → 模型理解消息，提出记忆/计划更新及下一步动作
    → 执行工具并取得实际结果
    → 更新相关条目、进度和变化关系
    → 若任务仍需继续，围绕新状态再次选择动作
    → 形成业务结果并同步界面
```

记忆更新和计划更新尽量结合已有模型调用完成，不必为每轮额外创建多个独立模型角色。事件影响计算、金额计算、规则条件判断和页面更新继续由程序执行。

### 14.3 结果对象

可以让工具结果和回复共用一个面向业务的结果对象：

```json
{
  "company": "C001",
  "period": "2026-09",
  "completed": [{"invoice": "F002", "action": "purpose_saved", "operation_ref": "..."}],
  "pending": [{"invoice": "F009", "reason": "waiting_for_user_information"}],
  "basis": [{"rule_id": "R002", "version": "2.0"}],
  "next_action": "wait_for_user",
  "reply": "F002的用途已保存，F009保留为待核实。"
}
```

金额、规则门槛、日期与数量分别关联对应语义字段和数据来源；保存声明关联实际操作结果。表达仍由模型结合当前问题组织，避免把所有回复固定为同一张长表。

### 14.4 一个完整模块可以怎样划定

建议把“**变化发生后的任务接续**”作为完整模块边界：

- 输入：用户补充/更正、规则更新、业务数据更新或恢复请求。
- 内部：任务记忆、影响计算、计划调整、相关上下文选择。
- 输出：正确的下一步工具动作或必要问题，以及更新后的实际任务进度。
- 交互：用户能查看、调整并继续该任务。
- 生命周期：从创建目标，到多轮变化、暂缓、恢复，再到完成或取消。

主动问询规划可以成为这个模块中最具用户感知的强项；经验手册则进一步改善它的策略。Claude 可据此判断核心边界是否合适，或提出更有价值的切分。

## 15. 实验设计：用真实任务筛选机制

### 15.1 需要回答的实验问题

| 机制 | 最重要的问题 |
|---|---|
| 任务记忆 | 能否接住超过近期窗口的目标、待确认项和更正关系？ |
| 影响驱动计划更新 | 变化后能否只处理必要部分，并继续完成目标？ |
| 主动问询 | 能否减少重复回答和无效追问，同时完成更多实际工作？ |
| 上下文编译 | 输入更集中时，关键条件与任务表现是否保持或改善？ |
| 经验手册 | 办理经历能否改善新的任务，而不仅是熟悉的例子？ |
| 任务地图 | 用户能否更快理解当前状态、改正目标和继续办理？ |

### 15.2 对照组建议

| 组别 | 内容 | 用途 |
|---|---|---|
| A0 | 当前最近 8 轮＋结构化任务/偏好 | 现状基线 |
| A1 | 全历史输入 | 信息充足时的参照，以及费用/延迟参照 |
| A2 | 常规滚动摘要 | 比较任务账本与摘要方法 |
| A3 | 语义检索式记忆 | 比较相似召回与任务关系选择 |
| A4 | 任务账本＋任务相关上下文 | 观察记忆结构贡献 |
| A5 | A4＋依赖影响与计划更新 | 观察变化处理贡献 |
| A6 | A5＋主动问询规划 | 观察交互效率贡献 |
| A7 | 胜出组合＋经验手册 | 观察策略学习贡献 |

组别用于研究问题，不要求一开始把全部组合都跑完。可以先选最能区分候选的任务，投入调参与适配；再对有潜力的组合做完整场景测试。对外解释某个部件的贡献时，再采用条件一致的对照或移除实验。

### 15.3 场景库

沿用原方案的 TaxMemBench-mini 思路，覆盖：

- 超窗口信息保持；
- 连续更正；
- 企业与用户切换；
- 规则变化；
- 外部业务数据更新；
- 保存中断与恢复；
- 缺依据、无权限和无记录；
- 多票口语回复、否定、暂缓与部分回答。

可以保留原方案约 60 个任务的场景库规模，并增加程序生成的新企业、编号、金额、规则和组合。官方样本检查与扩展实验分别组织。

对于多轮任务，先使用可重复的用户脚本、固定补充信息和数据库状态变化；再加入人工自由交互。这样可以把模型选择的差异与用户输入变化分开观察，也能控制实验费用。

### 15.4 判定与指标

核心结果看任务结束后的数据库状态、任务范围和未完成事项，同时记录：

| 方面 | 观察指标 |
|---|---|
| 完成能力 | 任务完成率、保存对象/字段正确性、规则和状态正确性 |
| 变化适应 | 旧值误用、目标遗漏、需重做的范围、恢复完成情况 |
| 交互效率 | 不必要追问、用户重复输入、人工补充轮数、返工次数 |
| 运行效率 | 输入/输出 token、调用数、完成耗时、单位成功任务费用 |
| 稳定性 | 同一任务重复运行的成功情况，关键任务可用 pass^3 |
| 产品体验 | 用户定位待办、理解更正影响和恢复办理所需时间 |

越权写入、改错字段、重复写入、保存误报单独列出。它们直接影响能否完成业务，不和轻微表达差异混在一起。

原 TaskLedger 的期望目标包括：困难类别成功率相对现状提高 15 个百分点、输入 token 不超过全历史方案的 40%、无效追问降至现状的 60%。这些可作为研究目标交给 Claude 讨论；最终采用哪组目标，应结合基线表现和实际任务价值确定。

### 15.5 经验改进的任务划分

策略发现用训练任务；策略选择与调参用开发任务；选定版本后再运行留出任务。留出结果不用于反复选取同一轮策略。一次完整任务实验从独立初始业务状态开始，便于比较最终结果。

### 15.6 预算怎样用于推进研究

研发继续使用 DeepSeek V4.1 Flash。按“场景数 × 平均轮数 × 每轮调用数 × 实际 token”估算每组实验成本；复用现有轨迹、确定性检查和脚本化用户输入。

不同机制尽量在同一模型调用循环中工作：记忆和计划更新可随理解结果一起输出，程序完成事件影响计算，避免为了模块名称增加大量额外模型请求。交付前集中用 Qwen3.8-Max 检查选定组合。

原方案估计的数千次调用作为工作量参考，不直接当作已经批准的执行预算。希望 Claude 帮助设计“哪些实验最能改变决策”，把资金用在有区分度的场景上。
